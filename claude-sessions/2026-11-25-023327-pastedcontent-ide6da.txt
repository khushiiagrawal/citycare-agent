  1. How the naive agent works, and where chaos breaks it

  How it works: one Sonnet prompt with all 8 tools, in a while True loop. The
  patient's phone is pasted into the message text. Model calls a tool,
  hospital_client runs it, result goes back, repeat until the model stops
  calling tools.

  Rule breaks (these fail even on a calm day):
  - Own data: the model fills in phone and appointment_id itself. "Cancel A1001"
    from the wrong phone works, and so does a prompt injection. The mock checks
    nothing, so nothing stops it.
  - No confirm gate: the model can book or cancel in one shot.
  - No 4-hour rule: A1002 (Arjun, today 12:00) gets cancelled with no handoff.
  - No emergency, medical-advice or facts rules: hospital_info.md is never
    loaded, so fees get invented. Reply is always agent: "naive", handoff: 
    false, emergency: false.
  - Time: the model guesses "today" and "Friday" from nowhere. It never calls
    /now.

  Bad-day breaks (chaos):
  - Any 503 or 409 crashes the run. raise_for_status() throws, /chat returns
    500, and the failed tool call stays in HISTORY without a tool_result. The
    next Anthropic call for that session then fails with a 400, so the session
    is dead for good.
  - Saved-but-failed writes (5%): the write lands, the hospital returns 503, and
    nothing verifies. The model says "failed". Patient retries and gets a
    double booking. This breaks rule 9. There is no idempotency_key.
  - Races (10%): 409 crashes the run instead of re-fetching slots and offering
    new ones.
  - Latency and load: the sync Anthropic client and sync httpx run inside async 
    def, so one slow call blocks every other chat. No timeouts or retries.
  - Runaway cost: no loop cap, no token or cost budget. Sonnet is used for
    everything. HISTORY grows forever.
  - Unsafe dispatch: getattr(hospital, name)(**args) lets the model call any
    attribute of that module, such as _get, with any kwargs.
  - Other gaps: no trace, and empty text on max_tokens or refusal.

  3. Build plan (one commit each)

  Design decisions up front:
  - Loop: async, takes a client with messages.create. It awaits the result if it
    is awaitable, so both AsyncAnthropic and the sync FakeClaude work.
  - Hook points: before_tool, after_tool, before_model and on_finish. They are
    generic, and the hospital rules plug in from outside.
  - Hook outcomes: a before-hook returns allow, deny(reason) or modify(input). A
    deny becomes an is_error tool_result, and the model sees why.

  agentcore (generic):
  1. Scaffold + CLAUDE.md + import-guard test.
  2. Core types: Tool (name, schema, async handler, writes: bool), Registry,
     RunContext (generic state dict plus a per-run id), RunResult.
  3. The loop: parallel tool calls, a max_turns cap, handling for max_tokens and
     refusal, tool exceptions turned into is_error results, unknown tool names
     rejected. Tests use FakeClaude.
  4. Hooks: the hook protocol and the four points. Tests for deny, modify, and
     after-hook rewrite.
  5. Tracer + cost: every model call and tool call recorded with timing, tokens
     and cost. The price table is passed in, not hardcoded.
  6. Session store: an interface with an in-memory implementation. History
     trimming. Never persist an orphan tool_use without its tool_result.
  7. Budget guard: per-run token/cost/time ceilings, and model-call retry with
     backoff on 429/5xx/timeout.

  Hospital layer (agent_service/):
  8. Async hospital client: timeouts, retries on 503, and typed errors
  (SlotTaken etc.). Writes always send an idempotency_key. After a 503 on a
  write, the tool code checks list_appointments before reporting the outcome.
  Code does this, not the model.
  9. Hospital tools: phone is bound from context and is not in any tool schema.
  A get_now tool reads /now.
  10. Safety hooks (the core):
      - Ownership: before_tool checks that any appointment_id or bill_id belongs
  to the session phone.
      - Confirm gate: a propose_* tool builds the read-back from real data and
  stores a pending action. The write tool executes only if the pending action
  matches the args exactly and was proposed in an earlier turn. The model judges
  whether the patient's reply is a yes. Code enforces that propose and execute
  never happen in the same turn.
      - 4-hour rule: before_tool on cancel/reschedule compares the slot with
  hospital /now. If it is inside 4h, it denies and sets handoff=True.
      - Failure counter: two failures in a row on the same request sets handoff
  (rule 8).
      - No /_admin access: nothing in the tool set can reach it.
  11. Emergency pre-check: a deterministic multilingual matcher (English, Hindi
  in Devanagari, Hinglish) that runs before the router, plus a "sticky" flag on
  the session. It leans toward false positives. Returns agent: safety,
  emergency: true, a 108 reply, and a handoff flag.
  12. Router (Haiku) + agents:
      - Router chooses booking, billing, info or human. It also has an emergency
  flag as a second net.
      - Info agent has hospital_info.md in its cached system prompt and no
  hospital tools.
      - Booking and billing get their own tool subsets, and every agent has a
  handoff tool.
      - I'll check the docs for how to force router output on Haiku 5.5.
  13. Wire up /chat and /trace/{session_id}. Remove the naive agent. Contract
  fields stay unchanged.
  14. Evals: run the 10 scenarios once calm to catch bugs, then add scenarios 11
  to 13. Candidates: a race loss followed by a slot re-offer; commit-then-fail
  with no double booking; cross-patient cancel by injection; Devanagari

  15. Docs: DESIGN.md, EVALS.md (per-run pass rate and failure causes), README

  How it works (code is in agentcore/types.py; loop.py now calls tool.parse):
  - Registering a tool:
  @registry.register(BookArgs, writes=True)
  async def book(args: BookArgs, ctx): ...
    The name defaults to the function name and the description to its docstring.
    If a tool has neither a description nor a docstring, building it raises an
    error, because the model reads that text.
  - Schema: it comes from the pydantic model, with the noisy title keys removed
    to save tokens. A field that is itself called title is kept.
  - Validation: strict, in JSON mode.
    - The string "3" for an int is an error, true for an int is an error, and
      1.5 for an int is an error.
    - "2026-12-04" for a date field is accepted.
    - Unknown fields are rejected even if the model class allows extras. This
      uses a subclass, so your own class isn't changed.
  - Errors:
    - The model gets one is_error result listing every problem, for example
